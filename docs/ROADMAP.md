# Roadmap

Where gpplus is, and what is left before it is a library other people can rely
on. Written to be picked up cold — by another agent, or by whoever next has a
Windows machine in front of them — so each item names its files, its
constraints, and how to verify it on a machine that cannot build it.

## Where it stands

Five backends: macOS (GameController and raw IOKit HID), Linux (evdev),
Windows (XInput and DirectInput 8), plus a synthetic one for tests. The
mapping database is fetched at configure time, filtered to the target
platform and compiled in. There is a rebinding recorder, battery reporting
on every backend that can answer, and rumble everywhere except raw HID.

The build is clean under `-Werror`, three test binaries pass locally, and the
FetchContent, `find_package` and offline-build paths are verified. CI is
green on all three platforms, and it has shown more than a build:

- **evdev** links, and the uinput test passes against a real kernel device,
  including the SDL-compatible numbering.
- **XInput and DirectInput** build and link under MSVC with `/W4 /WX`.
- **DirectInput** has been driven end to end by an emulated DualShock 4
  (ViGEmBus): found, mapped by the real database line, every button, the hat
  and all six axes correct. That run found a real bug, since fixed; see
  section 1.

What that does *not* cover, and the reason the checklist below is mostly
verification rather than code: **XInput has never run** (a hosted Windows
Server image has no Xbox 360 driver, so the emulated pad never starts), the
DirectInput `ig_` filter that stops an Xbox pad being reported twice has
never been exercised, and no backend on any platform has met a physical
controller. Everything below is either closing that gap or shipping.

## Ground rules

Read these before touching a backend. They are the invariants the existing code
is built on, and breaking one produces a library that compiles and is subtly
wrong.

- **No `#ifdef` for the platform inside a backend source.** Whether a backend
  is compiled is decided by a `try_compile` probe in
  `cmake/GpplusBackends.cmake`. A file that cannot build on this platform is
  never handed to the compiler. Adding a backend is one new source file, one
  detection block, and one line in the CI matrix.
- **Backends register through generated code.** CMake writes
  `gpplus_backends.inc` — one `GPPLUS_BACKEND(id)` line per surviving backend —
  and `src/backend.hpp` and `src/context.cpp` include it to declare and call
  `detail::make_backend_<id>()`. Nothing else needs editing.
- **Two kinds of backend.** Pre-mapped (`backend_mapped = true`: GameController,
  XInput) report `Button` and `Axis` directly. Database-mapped (evdev, IOKit
  HID) report numbered raw inputs and the database converts. Pick one; do not
  half-map.
- **Conventions live in the core, not in backends.** Deadzones, the Y-axis
  flip, trigger rescaling and edge detection are all in `src/context.cpp`. A
  backend reports what the hardware said, with stick Y **down-positive** and
  triggers **0..1**, and nothing else.
- **Raw input numbering must match SDL's**, or database lines silently rebind
  to the wrong buttons. `src/backend_evdev.cpp` documents the two-pass key
  ordering and why a tidier one would be wrong; a Windows raw backend has the
  same obligation.
- **Everything testable is tested through the virtual backend**
  (`include/gpplus/virtual.hpp`), because CI runners have no USB ports.

Build and test:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo -DGPPLUS_WERROR=ON
cmake --build build -j
ctest --test-dir build --output-on-failure
./tools/check-foreign-backends.sh    # type-checks the backends this machine cannot build
git ls-files '*.cpp' '*.hpp' '*.mm' | xargs clang-format --dry-run --Werror   # 16.0.6, as CI
```

`tools/check-foreign-backends.sh` fetches the real Linux UAPI headers and the
real mingw-w64 Windows headers and runs `clang -fsyntax-only -Wall -Wextra`
over the foreign backends. It catches typos, wrong struct fields and wrong
constants. It does not prove linking or runtime behaviour — CI does that, and
the CI jobs pass `GPPLUS_BACKEND_<NAME>=ON` so a backend that quietly stops
compiling fails the build instead of vanishing from it.

## 1. Windows: a backend for non-XInput hardware — done, run against an emulated pad

`src/backend_dinput.cpp` is a DirectInput 8 backend for the hardware XInput
cannot see. DirectInput rather than Raw Input because the database's ~870
`platform:Windows` lines were generated by SDL against DirectInput's
enumeration order, and that order is the entire meaning of `a0` and `b3` in a
mapping line.

- [x] Builds and links on the Windows CI runner under MSVC.
- [x] Numbering checked against an emulated DualShock 4 and its real database
      line. **This found a bug:** `EnumObjects` reports each object's offset
      in the *device's own* layout, not `DIJOYSTATE2`'s (on the DS4 it listed
      Rz at 0 and the buttons at 212), so trusting it read the first four
      axes right by coincidence and the last two from the always-zero
      sliders. Axes are now placed by their type GUID (X, Y, Z, Rx, Ry, Rz,
      slider), which is how SDL does it. Buttons and hats were never affected.
- [ ] Confirm on real hardware that a non-XInput device — an arcade stick, a
      flight yoke, an old USB pad — is found, mapped from the database, and
      reports the right buttons. The emulated DS4 is one layout; the point
      of the check is that an axis order that differs from SDL's makes every
      Windows mapping subtly wrong rather than obviously broken.
- [ ] Confirm an Xbox pad is reported exactly once, not twice. The `ig_`
      path test is what prevents the double, and it has never executed: the
      hosted runners cannot start an emulated Xbox pad. Run
      `cmake -S . -B build -DGPPLUS_TEST_VIGEM=ON -DGPPLUS_BACKEND_XINPUT=ON
      -DGPPLUS_BACKEND_DINPUT=ON` and `ctest --test-dir build -R vigem` on a
      Windows 10/11 client machine with ViGEmBus installed; the Xbox phase
      there covers XInput, rumble and this check in one go.
- [ ] Force feedback is deliberately absent (`caps.rumble = false`); see
      "Later".

## 2. A rebinding API — done

`include/gpplus/binding.hpp` and `src/binding.cpp`. `MappingRecorder` takes a
baseline, watches the raw inputs, and reports the one the player meant:
buttons beat hats beat axes, the furthest-moved axis wins, and a detection has
to hold for a few frames before it counts. `mapping_line()` emits the
database line; `apply()` installs it live.

Covered by `tests/test_binding.cpp` — 65 checks, all through the synthetic
backend, including the two that are easy to get wrong: an axis that answers
"push right" by falling is written `a0~`, and a trigger is written whole or as
a half depending on where it rests, which is the difference between a released
trigger reading 0.0 and reading 0.5.

`examples/rebind.cpp` walks a player through a whole pad and prints the line.

- [ ] Try the walkthrough on real hardware, ideally on a pad with no database
      entry. The prompts and the release-detection between them are the part
      that only reads right with a controller in hand.

## 3. Battery and power reporting — done, partly unrun

- evdev reads `capacity` and `status` (falling back to `capacity_level`) from
  the power supply the kernel hangs off the input device in sysfs, on the
  hotplug tick rather than every frame. No power supply node means wired.
- XInput resolves `XInputGetBatteryInformation` at runtime through
  `GetProcAddress`, because `xinput9_1_0` does not export it and linking it
  would trade battery reporting for a build that does not link at all.
- The thresholds match the GameController backend's, so a game drawing a
  battery icon does not have to know which backend it is on.

`tests/test_context.cpp` covers the plumbing through the synthetic backend and
`tests/test_uinput.cpp` asserts the wired case on a real kernel device.

- [ ] Confirm against a wireless pad on Linux and on Windows that a real
      battery level comes through. Only the "no battery" path has been
      exercised.

## 4. Simulated hardware in CI

**Why.** Everything except the Linux path is verified by a type checker and a
synthetic backend. Neither can catch an ioctl with the wrong argument, a
capability query read from the wrong field, or a button numbered differently
than the database expects. Injecting real events is the only thing that can.

What is possible differs sharply per platform, and it is worth being blunt
about it.

- [x] **Linux — uinput. Done.** `tests/test_uinput.cpp` asks the kernel for a
      gamepad through `/dev/uinput`; from that moment it is indistinguishable
      from hardware, and the evdev backend finds it by scanning `/dev/input`,
      enumerates it with the same ioctls it uses on a real pad, and reads real
      events off a real descriptor. It asserts the SDL-compatible numbering by
      spelling out a mapping that says `a:b0` and letting the kernel decide
      what button 0 is. CI loads the module and runs that one test as root,
      because the node udev creates is `root:input 0600`. It passed on its first
      CI run.
- [x] **Windows — ViGEmBus. Half runs on hosted CI.** `tests/test_vigem.cpp`,
      behind `-DGPPLUS_TEST_VIGEM=ON`, and the `windows-vigem` CI job.
      [ViGEmBus](https://github.com/nefarius/ViGEmBus) is a signed kernel
      driver that emulates game controllers; the test plugs in two and
      drives both Windows backends through them. The driver installs on a
      hosted runner with `choco install vigembus` and starts.
        - *DualShock 4 → DirectInput. Runs and passes in CI.* Mapped by the
          **real** database line (`a:b1,b:b2,x:b0,y:b3,…,righty:a5`) rather
          than one written for the test. That line is DirectInput's
          enumeration order, so this is the check on the numbering; it is what
          found the offset bug in section 1.
        - *Xbox 360 pad → XInput. Cannot run on hosted CI.* Every button,
          both sticks, both triggers, rumble coming back out of the driver,
          and the pad reported **once**. The bus accepts the pad but Windows
          Server 2025 has no inbox Xbox 360 driver for it to bind to (the
          node sits in `CM_PROB_FAILED_INSTALL`), so the phase skips, says so
          loudly, and CI raises a warning annotation. `vigem_target_add`'s own
          error for this is misleading: it reports `TARGET_NOT_PLUGGED_IN`
          from its cleanup call and discards the real one. The phase is
          written and type-checked, and unrun anywhere; see section 1 for
          running it on a client machine.

      It type-checks against the real ViGEmClient headers via
      `tools/check-foreign-backends.sh`. The job is `continue-on-error`, and
      turns a run where nothing executed into a failure so it is not a green
      one. Promote it to required once it has been stable.

      **ViGEmBus is retired upstream.** No further releases; 1.22.0 is the
      last, and the job is pinned to it. It works today, but a future
      Windows update can break it for reasons that are not this library's,
      which is a second reason to keep it non-blocking. If it ever does, the
      DirectInput numbering check has no substitute short of real hardware.
- [ ] **macOS — not possible, and the roadmap should stop pretending
      otherwise.** There is no supported way to create a virtual HID device
      without a DriverKit system extension, and installing one needs an
      approval click a runner cannot give. GameController has no injection
      API at all. The macOS backends stay at unit tests, compile checks and a
      manual smoke test; that is the honest ceiling, and it is why the
      hardware smoke test below is a real checklist item rather than a
      formality.

## 5. Release

- [x] Fix the placeholder URL in `README.md` and `CMakeLists.txt`; both now
      point at `https://github.com/SeedyROM/gpplus.git`.
- [x] Add `CHANGELOG.md` with a `0.1.0` entry.
- [x] Create the GitHub repo, add the remote, push `main`.
- [x] Watch the first CI run. It took several rounds, as predicted: the
      DirectInput probe needed linking by name, MSVC's C4996 rejected
      `getenv` under `/WX`, `cmake --install` needed `--config`, and the uinput
      job grepped for text ctest never prints. Six jobs must stay green:
      `clang-format`, `linux-evdev`, `macos-gamecontroller-iokit`,
      `windows`, `consume-via-fetchcontent` and `no-network-build`.
      `windows-vigem` is not on that list: it may fail without failing the
      run, and its result is worth reading.
- [ ] **Smoke-test on real hardware** — needs a human with a pad. Run
      `./build/examples/gpplus_probe`: the device should be identified, the
      mapping should match, every button and axis should report, South should
      rumble, and the battery line should say something true. Then
      `./build/examples/gpplus_rebind` for the recorder. Repeat per platform where possible; the macOS backends
      have only ever been exercised against zero devices.
- [x] Decide on `GPPLUS_CONTROLLER_DB_SHA256`. **Unpinned by default.** The
      default URL is upstream's moving `master`, so a baked-in hash would fail
      every fresh build as soon as upstream commits; the worst a stale or
      missing database does is leave a pad unmapped. Reproducible builds pin
      the URL to a commit *and* the hash, which the README now documents. Both
      halves are verified: the pinned pair configures, and a wrong hash fails
      the configure (exit 1) rather than falling back quietly, while network
      failures still fall back softly.
- [x] Tag `v0.1.0-alpha`. A pre-release of 0.1.0, because nothing has met a
      physical controller yet. The FetchContent `GIT_TAG` in `README.md` and
      `CMakeLists.txt` names it, and `CHANGELOG.md` carries the date and a
      "Known limitations" section that says plainly what has not been run on
      real hardware.
- [ ] Tag `v0.1.0` once the hardware smoke test above has passed on at least
      the platforms you can reach, and the alpha's known limitations have
      either been closed or been restated honestly. Update `GIT_TAG` in
      `README.md` and `CMakeLists.txt`, the changelog heading and the README
      status note to match.

## Later — not blocking v0.1.0

- **Force feedback for macOS HID pads.** `src/backend_iokit.mm` reports
  `caps.rumble = false` because rumble there means ForceFeedback.framework —
  `FFDeviceCreate`, `FFDeviceCreateEffect` with a periodic or custom-force
  effect — a second protocol with its own lifecycle, for a set of devices that
  is mostly empty, since the pads with motors are the pads GameController
  already claims. Worth doing when someone turns up with a rumbling stick that
  GameController refuses; not worth doing speculatively. The hook is ready:
  implement `Backend::rumble` on `IokitBackend` and flip the capability.
- **DirectInput force feedback** on Windows. `IDirectInputEffect` with a
  constant or periodic force, for the wheels and sticks that have motors.
  Same reasoning as above: the mainstream pads are XInput's, and XInput
  already rumbles them.
- Gyro, touchpads, adaptive triggers, and LED patterns beyond a single colour.
